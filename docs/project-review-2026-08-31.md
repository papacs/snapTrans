# snapTrans 整体评估与优化路线

评估日期：2026-08-31  
代码基线：`daee7a8`（设置窗口进一步优化，添加设置最小化到任务栏）

这次只做分析和验证，没有修改功能代码。结论来自代码审查、现有自动化测试、三个临时交互探针、本地历史耗时的数字汇总，以及 DeepSeek 官方文档。未调用用户的付费翻译接口，未完成 Windows 实机视觉、混合 DPI 和长截图兼容性验收；下面将“已确认行为”和“待测性能风险”分开描述。

## 整体判断

项目的核心定位清楚：快捷键 → 冻结屏幕 → 框选 → 松手即识别并原位翻译。这个路径应继续保持，不增加确认步骤。

现有基础已经包括 OCR 常驻预热、后端裁剪、内存图片地址传输、流式文本按动画帧合并、过期事件隔离、DPAPI 密钥加密、单实例锁、截图标注、长截图和历史记录。下一阶段的主要价值在于：把功能之间的行为统一起来，减少长尾等待，并让失败可理解、可恢复。

不建议此时更换 Wails/Vue 技术栈或一次性重写。最有收益的是先完成一次可靠性修整，再做有测量依据的性能优化。

## 1. 应优先处理的具体问题

优先级含义：P0 为默认使用或发布阻断风险；P1 为常见操作正确性/可靠性；P2 为体验与工程打磨。这里的优先级不是安全漏洞等级。

| 优先级 | 已确认的问题 | 用户影响 | 建议及验收 |
| --- | --- | --- | --- |
| P0 | 默认模型仍为 `deepseek-chat` | 新用户使用官方 DeepSeek 默认配置可能无法翻译 | 按服务商处理默认值和迁移提示；官方服务使用当前支持模型，并验证非思考模式。不能擅自替换自定义 LiteLLM 模型别名 |
| P1 | 测试连接读取后端已保存配置，没有接收当前表单 | 刚填的新地址、新 Key、新模型并没有被测试；成功/失败都可能误导 | 传入独立的连接测试参数，只测试、不保存、不更改快捷键或 OCR。验收：改成无效地址后立即测试，确实测试无效地址 |
| P1 | 取消设置仅隐藏表单，不恢复配置；部分前端选项已立即参与工作流，开机自启则直接写注册表 | 用户点“取消”后，下次翻译行为仍可能变化，且前后端配置不一致 | 分离 savedConfig 和 draftConfig。保存统一提交；取消回滚；最小化保留草稿。若保留立即生效的选项，应明确标注并改变取消语义 |
| P1 | 流式翻译已有文字时发生错误，前端直接进入 done 并清空错误 | 不完整结果看起来像已完成，且没有重试入口 | 增加 partial 状态：保留译文、标注未完成、可复制/重试缺失部分。补译后重新核验缺失行，不能只发出 done |
| P1 | 保存 OCR 路径后，先写入 a.cfg，再由 syncOCRWorker 与 a.cfg 比较；两者已经相同 | 常驻 OCR 不会因路径变化执行预期重启；现有 worker 的超时也未更新 | 使用保存前配置比较，或由 worker 持有并比较完整有效配置。验收：路径 A→B、超时变化、预热开关切换均不需重启应用 |
| P1 | Esc 只处理设置和 loading/ready/drawing/editing，没有覆盖 processing/streaming/done/error | 最需要快速退出时，常用退出键不一致 | 统一窗口/工作流状态表；Esc 在结果及等待阶段取消任务并收起。保留文本编辑器内部 Esc 的优先级 |
| P1 | GitHub Actions 的后端 job 在 Ubuntu 执行整个项目，而入口和 singleinstance 直接依赖 Windows 包 | 本机测试通过不代表 CI 可通过，发布质量门槛不可靠 | Windows job 执行完整 Go 测试；Linux 只测真正跨平台模块，或补齐正确的构建隔离 |

### 默认模型兼容性

DeepSeek 官方公告将 `deepseek-chat` 和 `deepseek-reasoner` 的停用日期列为 2026-07-24；本次评估已晚于该日期。当前官方模型表使用 `deepseek-v4-flash`、`deepseek-v4-pro` 等名称。[官方更新记录](https://api-docs.deepseek.com/updates/)、[当前模型表](https://api-docs.deepseek.com/quick_start/pricing/)

当前模型表还注明默认开启思考模式。对截图翻译，应以非思考模式作为候选默认配置进行首字延迟与译文质量验证，不能只替换 model 名称。具体协议参数应由服务商适配层处理，避免发给不支持该字段的兼容服务。[官方思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode)

以上是文档兼容性结论，不代表已经测试了用户当前账户或自定义网关。已有自定义模型名必须保留。

### 另外几处值得顺手修整的细节

- 本地快速词典在自定义提示词/术语表之前直接返回，可能绕过用户指定术语。应明确优先级：用户术语优先；不能覆盖时再走默认快速词典。见 [快速返回路径](E:/workspace/snapTrans/app.go:994)。
- 历史记录保存的是原始流式译文，可能含内部 `[n]` 编号，而结果页复制使用清理后的文本。历史显示和复制应复用同一标准化逻辑。
- OCR “ready” 当前主要表示找到可执行文件，不等于模型已加载或 worker 健康。建议分别显示“文件可用 / 正在预热 / 已就绪 / 已回退”。见 [环境检查](E:/workspace/snapTrans/app.go:1114)。
- 读取历史失败目前会表现成空列表；清空失败被忽略。错误应有可见反馈，避免把失败当成成功或没有记录。

## 2. “更丝滑”应该优先优化哪里

### 已有日志中的耗时

仅汇总本地日志中的数字，没有输出 OCR 文本、密钥或请求内容。读取末尾 2500 行，每个指标独立取最近 50 个匹配样本，P95 使用最近秩法。读取窗口覆盖 2026-08-04 至 2026-08-31，包含不同历史版本和使用场景，样本之间不保证一一对应，不能将各行相加。

| 指标 | 中位数 | P95 |
| --- | ---: | ---: |
| 触发截图到界面就绪 | 196 ms | 1120 ms |
| 抓屏 | 51 ms | 100 ms |
| 截图编码 | 13 ms | 56 ms |
| 后端选区裁剪与编码 | 18 ms | 134 ms |
| OCR | 499 ms | 2971 ms |
| OCR 工作流开始到首个译文 token | 2781 ms | 16626 ms |
| 进入翻译阶段到首个译文 token | 2005 ms | 13643 ms |

这些是历史观察，不是当前版本的受控基准。首 token 的工作流计时不包含前面全部裁剪和 UI 操作；翻译等待样本也可能混入本地词典路径。因此只能用来确定排查顺序，不能用于声称某个服务商或当前版本的精确性能。

方向很明确：优先降低 OCR 和 API 的长尾等待，再处理局部绘制开销。现有前端产物约 260 KB JS、44 KB CSS，没有足够证据把体积当作当前第一瓶颈。

### 建议的性能改动

1. **重试、反向翻译复用已完成的 OCR。**  
   现在反向和重试仍走 TranslateRegion → 裁剪 → OCR。保存当前选区的 OCR 文本和 blocks，以“截图 ID + 选区 + OCR 配置”标识；网络失败只重试翻译。可直接去掉一次重复 OCR。译文缓存还必须包含方向、服务地址、模型、提示词与术语表，不能只按原文缓存。见 [反向/重试](E:/workspace/snapTrans/frontend/src/App.vue:895)。

2. **去掉抓屏后 Go 内部的一次 PNG 回解码。**  
   目前抓屏拿到像素 → 编码 PNG → App 再 png.Decode 保存 frame → 之后裁剪。可以让捕获结果同时提供受控生命周期的原始帧引用与前端图片地址。OCR 仍需按协议编码，但无需在 Go 内部先编后解整屏。见 [抓屏实现](E:/workspace/snapTrans/internal/capture/capture.go:112)、[再次解码](E:/workspace/snapTrans/app.go:861)。

3. **图片缓存按字节预算和消费确认释放。**  
   当前最多保留 8 份图片，无压缩全屏 PNG 并不小，隐藏窗口只释放 a.frame，没有清掉这份图片缓存。这是有上限的保留，不是已证明的无限内存泄漏。4K RGBA 单帧理论约 31.6 MiB，多份图像与 WebView 像素副本叠加可达到较高内存占用。建议前端解码确认后回收旧帧，关闭/取消时清理无用资源，并防止提前删除正在解码的图。见 [图片缓存](E:/workspace/snapTrans/capture_asset.go:24)。

4. **将 OCR 区块的背景/前景采样从逐 token 布局中分离。**  
   两套 computed 布局依赖译文；变化时会再次调用 getImageData，背景和前景还分别读取。优先在 OCR blocks 到达时一次采样并缓存，只重算变化的文本行；动态扩宽区域另行控制采样范围。若样本显示主线程压力，再考虑 Worker/OffscreenCanvas。见 [区块布局](E:/workspace/snapTrans/frontend/src/App.vue:321)、[像素读取](E:/workspace/snapTrans/frontend/src/utils/selection.ts:445)。这是代码确认的重复工作，实际收益仍须性能面板测量。

5. **画笔按动画帧绘制，缓存已完成笔画。**  
   现在每次 mousemove 都复制整段 points 并重绘所有标注；长笔画和大量标注时成本增长。将采样与绘制分开，每帧最多刷新一次，完成笔画进入独立缓存层；保留矢量数据供撤销与导出。见 [标注移动/重绘](E:/workspace/snapTrans/frontend/src/components/ScreenshotEditor.vue:438)。

6. **分开 OCR、首 token、流式空闲和总体超时。**  
   当前 translationTimeoutSeconds 从 OCR 之前开始计时，名称与实际语义不完全一致。应明确每个阶段的预算；API 长时间没首字时显示可恢复提示，流式中断保留部分内容。重试要有次数和总时长上限，禁止无界循环。

7. **同步编码与长截图轮询按测量调整。**  
   普通截图导出、提取文本使用 toDataURL，可能在大图上阻塞 UI；优先复用后端选区 OCR，导出使用异步 Blob 或原生图片路径。长截图当前约每轮完成后 180ms 再采集，建议静止时降频、有变化时恢复，并保持请求串行。不要为了快而改用会损坏小字的有损截图格式。

### 建议建立的受控验收

- 固定同一台参考设备，分别测 1080p、4K；OCR 冷启动/热启动；单词、段落、表格；分别记录真实服务和本地模拟服务。
- 先建立 30 次以上重复样本的中位数/P95，再决定预算。候选交互目标：松手后 100ms 内出现状态反馈；参考设备热启动截图界面 P95 争取低于 300–350ms。它们是拟定目标，不是现有达标结果或跨设备承诺。
- API 首字耗时单独展示和统计，不与本地绘制耗时混为一谈，不承诺网络请求必定在固定秒数内完成。
- 连续截图 20 次、取消/关闭后检查驻留内存回落；长笔画和 100 个标注下检查主线程长任务。
- 现有截图编码 benchmark 仍调用包含 Data URL 编码的辅助路径；补充当前“原始帧 → PNG 地址 → 前端解码”的基准，避免优化错误的测量对象。

## 4. “更好看”的具体方向

这部分依据模板、样式和组件结构提出，尚未完成实际渲染截图验收。

### 设置页：降低层级噪声，让常用操作更容易找到

- 将长表单分为“常规 / 翻译服务 / OCR 与截图 / 高级”，历史放独立入口。首次使用优先呈现快捷键、服务连接和 OCR 状态。
- 保留 emerald 主色，减少每个区域都使用重阴影、渐变、环线和背景模糊的叠加。以清晰分组、对齐和留白形成层级。
- 统一字号与行高；正文和输入维持清晰可读，辅助说明避免大面积 11px 小字。统一 8/12/16/24 的间距与少量圆角规格。
- 保存按钮仅在有改动且有效时启用，显式显示“有未保存更改”；保存成功提供短暂反馈。字段错误紧邻字段，避免只在底部出现长英文消息。
- 主题增加“跟随系统”，并让表单控件的 color-scheme 与主题一致。中文/英文切换应覆盖托盘、截图工具栏、加载状态和错误提示，而非只覆盖设置页。

### 截图和结果：信息要让位于内容

- 工具栏使用统一的 32–36px 按钮、选中态、分组间距；低频操作进入“更多”。补充 focus-visible 与键盘说明。
- 框选时显示物理像素尺寸，必要时附缩放信息，避免高 DPI 下把 CSS 尺寸当作导出尺寸。
- 流式输出只更新变化行；已经完成的行尽量固定位置，减少后续文字引发的整体跳动。
- 复杂底图提供“优先可读”模式：稳定底色卡片和清晰对比度；不要让背景采样或前景颜色匹配压过可读性。
- 用 100–150ms 的少量状态过渡即可，不对每个 token 做动画。尊重减少动态效果设置。
- 对加载、无文字、识别失败、网络失败、部分完成、复制失败分别设计短句与对应操作。用户应知道“发生什么”和“接下来能做什么”。

## 5. 专业化与维护能力

### 拆分职责，但保持现有服务边界

当前 app.go 约 1264 行，App.vue 约 2134 行，ScreenshotEditor.vue 约 921 行。模块分离应随修复逐步进行：

- Go：窗口/托盘、配置应用、OCR 生命周期、翻译工作流、截图资产管理分别归位。
- Vue：SettingsPanel、TranslationOverlay、useCaptureWorkflow、useSettingsDraft、useTranslationLayout 等按职责拆开。
- 继续让 frontend/src/services/backend.ts 承接 Wails 与浏览器 fallback，不让组件直接混用底层桥接。
- 用明确状态转移和带类型的事件区分“工作流失败”和“全局配置/启动错误”。当前 generation 过滤会丢弃不匹配的配置错误；全局错误应有独立通道或可查询状态。

## 6. 建议分三轮推进

| 轮次 | 范围 | 完成标准 |
| --- | --- | --- |
| 第一轮：可靠性 | 官方模型预设；草稿/取消/连接测试；OCR 配置更新；partial 状态；全阶段 Esc；CI 平台修复；图片复制失败反馈；长截图上限提示 | 用户操作与结果一致，错误不伪装成成功，相关回归测试齐全 |
| 第二轮：速度和阅读 | OCR 结果复用；原始帧复用；缓存预算；背景采样缓存；画笔刷新合并；分阶段耗时；原文对照和可读模式 | 用同一组夹具和设备对比 P50/P95、帧耗时和内存；证明改动收益，保持无损截图 |
| 第三轮：外观与交付 | 设置页信息架构；统一主题/文案/键盘；历史面板；长图后编辑；发布资产、版本和文档统一 | 完成真实 Windows 视觉、DPI、首次使用和发布包回归 |

最先动手的组合建议是：**设置事务与连接测试、部分失败可见、Esc 全阶段退出、OCR 配置更新、官方模型兼容性**。这一组直接改善用户对工具的信任，同时不改变“松手即翻译”的核心习惯。
