# 截图回复助手与响应速度设计

目标是把“看消息 → 想怎么说 → 组织文字”变成一次框选，再由用户快速修订、复制使用。

## 使用流程

- `Alt+Q`：保持选词 / 截图翻译。
- `Alt+W`：保持截图标注。
- `Alt+R`：冻结屏幕 → 框选消息或帖子 → 松手直接生成回复；默认先识别文字，可切换直接看图。
- 已完成的翻译结果也可以点击“帮我回复”，复用原文，省去再次截图与 OCR。

三个快捷键可在设置中分别配置。托盘有对应的截图回复入口。

## 回复质量

默认一次输出一版简短、自然、可直接使用的回复，减少等待与选择负担。

| 场景 | 输出原则 |
| --- | --- |
| 自然得体 | 回应核心意思，友好且有边界，不机械附和 |
| 职场沟通 | 尊重、清晰、有行动性，不替用户编造完成进度、交付时间或承诺 |
| 社交评论 | 针对帖子具体内容表达观点或提问，避免空洞赞美和强行幽默 |

“我想表达”用于补充立场，例如“礼貌拒绝，说明排期已满”“先确认优先级”“赞同观点，再补充一个角度”。参考原文可以修正 OCR 结果；生成结果也可直接编辑。

修改原文、场景或意图后，需要重新生成才能复制，避免错用旧上下文的结果。模型仅生成草稿；复制由用户操作完成，发送仍在目标应用中由用户确认。

## 性能与稳定性

实测诊断显示，原链路存在三项延迟：每次启动进程、本机 `xhigh` 思考设置的继承，以及 WebSocket 连接重试。后者在本次网络环境中造成约 46 秒的首字等待。

改动采用 Codex 管理的订阅认证，并通过临时配置选择 HTTPS 流式传输，不修改用户的 Codex 配置文件。应用启动与开始框选时预热本地进程、登录和所选模型的会话准备，随后释放空白临时会话；预热不启动模型生成，不消耗生成额度。空闲进程保留 5 分钟。

进程可复用，每次生成仍使用独立临时会话。完成后释放该会话；取消或连接异常时丢弃进程。下次请求会重新建立连接，避免共享上下文或复用损坏的流。

默认轻量思考 `low`，适合翻译与短回复；配置页允许切换思考强度。模型推理、网络和服务端排队仍会影响首字时间，性能数字以实际日志为准。

前端立即显示回复面板，分别反馈“识别文字”“生成回复”；流式内容按动画帧合并更新。面板固定尺寸并避让屏幕边缘，减少布局跳动。复制、停止、重新生成和 Esc 关闭始终可达。

每次生成有独立请求 ID。关闭面板、再次截图、打开设置均取消旧请求；旧 OCR 结果和旧 token 不能覆盖新内容。停止保留已生成部分，复制失败保留草稿并反馈错误。

## 数据与边界

默认截图在本机 OCR，仅将识别文字和用户填写的意图发送给所选模型。AI 服务页可开启“直接看图 · 跳过 OCR”，截图翻译与回复会上传选区；回复面板可以单独切换。原文、截图和回复草稿保留在当前界面内存，不写入回复历史；仅记住场景偏好。

屏幕内容作为引用数据处理，与用户主动填写的意图分开编码。后端校验选区、文本长度和场景；回复专用提示词不继承翻译术语表或翻译提示词。

直接看图适合图片帖子、聊天气泡、说话人关系等视觉上下文。仅裁剪冻结帧中的物理选区；不做 OCR 放大，长边限制 1600 像素，JPEG 质量 90，内联传给视觉模型，不将截图写入临时文件。缩小过大的选区可能影响极小文字，建议只框选相关内容。选中文字继续直接使用文字通道。

视觉翻译整段输出；自动翻译方向在同一次模型响应中返回，不再追加识别请求。不具备 OCR 的文字块坐标，因此不支持逐块覆盖。历史仅记录译文和“截图直读”标记。模型图片能力由所选服务提供，不支持时显示错误，用户可切回 OCR，不静默发起第二次付费调用。

## 后续方向

优先从真实使用中验证默认回复质量，再考虑增加“委婉拒绝 / 推进事情”等快捷意图和用户常用表达偏好。暂不增加自动发送、常驻监听、复杂工作流和大量候选结果。

### OCR 与直接看图对照

同日进一步检查本机使用日志：OCR 约 65–606 ms，模型翻译等待约 768–5741 ms，部分回复首字约 3709–9494 ms。OCR 并非当前主要耗时。日志记录图片准备、模型首字与总首字耗时，便于区分本地处理和远端等待。

同一组合成职场消息使用已预热的 gpt-6-luna 订阅连接，依次测试：

| 输入 / 思考强度 | 首字 | 完成 |
| --- | --- | --- |
| 文字 / low | 4.54 s | 4.80 s |
| 文字 / none | 4.65 s | 4.97 s |
| 图片 / none | 5.13 s | 5.46 s |
| 文字 / none，再次 | 4.63 s | 4.95 s |
| 图片 / none，再次 | 5.24 s | 5.47 s |

这是顺序执行的小样本，不是模型通用性能排行；文字时间不含 OCR，图片时间不含裁剪编码。图片跳过了 OCR，但上传和视觉编码增加了开销，因此本组没有提速；关闭思考也没有显著收益。直接看图的主要价值是上下文和识别质量，不宜默认宣称更快。真实订阅截图翻译也已验证能自动识别方向并流式输出译文。

连接已预热且采用 HTTPS 后，剩余等待主要在模型首字；新建临时会话等本地 RPC 约几十至数百毫秒，复用会话还需要可靠清除上次截图上下文，收益不足以抵消隔离复杂度，因此保留每次独立会话。要进一步明显缩短等待，应在同一网络、同一输入下比较其他快速模型或 API 接入的实测首字，不能仅按模型名称推定速度。

本轮验证：`go test ./...`、183 项前端测试、TypeScript 检查和生产构建通过；Windows `snapTrans-vision.exe` 已生成。覆盖直接看图绕过不可用 OCR、图片输入协议、裁剪的负坐标与缩放限制、配置迁移、回复模式切换和无 OCR 原文时从视觉翻译进入回复。浏览器预览检查了设置页和回复面板布局；真实模型验证使用合成截图，未发送私人聊天。

### 复制原图问题与冷启动补充修复

用户反馈复制出来仍是英文。最近两次历史中的实际译文为中文；根因是图片复制仅调用 OCR 文本块绘制器，直接看图没有文本块，最后导出的就是原截图。另有纯文本面板半透明背景样式未生效的问题，会让原文透在译文后面。

修复后，没有文字块坐标的结果采用不透明的完整译文面板；保持 16 px 字号、24 px 行高，面板随内容扩展并可滚动。复制图片按实际 DPI 绘制完整译文卡片，避免裁掉末行。生成期间禁用图片复制，防止误用未完成的结果。对应回归测试已先复现失败，再验证通过。

性能补测：普通新进程短句首字 8.80 s、连续请求 3.52 s；另一次登录检查 6.26 s、模型列表 2.14 s。之前预热只到模型列表，首次 `thread/start` 仍可能花约 3 s。现在预热完成空白临时会话的建立与释放，实测将约 2.81 s 的会话准备移到后台；随后两次短句首字 3.63 s、4.53 s。服务端等待仍有波动，不能保证每次秒出。

同一短句用用户已有的 API 配置做一次对照：`deepseek/deepseek-v4-flash` 首字 2.50 s、完成 2.65 s。该测试未修改或保存接入设置，也没有输出密钥。以上为不同时间顺序执行的小样本，不是稳定性能承诺。

修复版验证：完整 Go 测试、185 项前端测试、类型检查与生产构建通过；Windows 输出为 `snapTrans-vision-fix.exe`。浏览器实际检查了小选区扩展、白底遮挡和复制成功反馈。新增断言检查导出时确实绘制中文译文而不绘制原截图，避免仅验证返回了 PNG 地址却漏掉内容。

### 翻译专用速度优化

用户选择继续使用 Codex 订阅，因此不切换翻译服务。新增默认开启的“翻译优先速度”：翻译使用精简的行号协议提示，已知支持 `none` 的 GPT-6 Luna / GPT-5.6 Luna 不启用思考。未确认能力的模型保留原强度，不猜测兼容性。回复、解释等操作保持用户原有思考设置。关闭速度开关可恢复原翻译提示与思考设置；术语、自定义指令及漏行检查继续保留。

为避免重复框选再次等待，成功译文在进程内存中保留最多 16 项，每项不超过 64 KiB，10 分钟有效。匹配输入内容、接入方式、端点、模型、方向和完整翻译选项的 SHA-256 摘要；只保存摘要与最终译文，不保存截图、原文或凭据。模型、方向或术语设置变化即不命中；取消、失败或部分输出不缓存。回复不复用生成结果，重新生成仍调用模型。

此前每次关闭或新截图都会清空最近一次 OCR 结果，即使截图完全一致也重复识别。现在保留最后一次成功 OCR，仍以完整图片摘要和 OCR 配置严格匹配；不同选区或不同 OCR 设置不会复用。已有的取消检查、结果副本与配置更换清理机制保持生效。

本轮真实订阅验证使用合成排期文本：英译中首次首字 3841 ms、完成 4181 ms，重复请求首字和完成均不足 1 ms；中译英首次首字 6803 ms、完成 7004 ms，重复请求同样不足 1 ms。以上均为模型阶段，不含截图与 OCR；两个方向的三行译文全部返回且缓存结果一致。新内容的远端首字仍有波动，本轮没有证据支持“首次翻译稳定秒出”。

自动化验证：完整 Go 测试、186 项前端测试、类型检查和前端生产构建通过，覆盖缓存容量与期限、设置失效、错误和取消不缓存、回复仍发起请求、视觉翻译方向复用、OCR 跨截图复用及速度设置迁移。Windows 产物为 `snapTrans-translation-fast.exe`。
